How a plan actually gets made

This is the sequence in SKILL.md, and it is a real sequence — each step only makes sense once the one before it is done. The references get pulled in at steps 4 and 5.

  1. Standards readiness gate. Confirm every Android rule the plan intends to quote is actually written down, not an empty placeholder. A placeholder says so in its own purpose line, so the check is a read, not a guess. It is expected to pass — it exists so the lane fails loudly if someone deletes a standard.
  2. Source of truth, then reuse what the repo already publishes. An approved scope or a recorded decision outranks a standard, which outranks Android's own documentation. Existing repo knowledge is reused rather than re-derived; the feature-specific detail is always read fresh.
  3. Collect the evidence. Eighteen dimensions of the codebase — Gradle setup, modules, SDK levels, UI toolkit, navigation, state, DI, networking, persistence, background work, concurrency, testing, reusable components, integrations, and the rest. Each finding is stamped with the file that proves it, or marked unknown.
  4. Identify the implementation model per surface. Compose, XML/Views, both, mid-migration, or something in-house. Per screen, not per project — a repository is allowed to contain several, and the surface the feature touches decides which rules apply.
  5. Branch on phone versus TV. Phone takes the standard path. TV opens tv-context.md and runs its discovery pass before anything is proposed.
  6. Compose the approach. Work through analysis-domains.md for every topic the feature touches, checking what already exists before proposing anything new.
  7. Classify every statement. Everything written down is one of four things: already there, genuinely required, recommended, or an open question. The three lists are never merged.
  8. Verify, fix, verify again. Run the plan against the Definition of Done. A failing item gets fixed and re-checked, not handed over with a note.

Inside analysis-domains.md

Twelve topics, plus a pointer at the top to where the screen’s UI model gets decided — that decision comes first, because several topics below resolve differently depending on it. Every topic the feature touches gets worked through; every topic it does not touch gets written down as N/A with the reason. Saying nothing is treated as a defect, not as “not applicable”.

The tags in green are the rule identifiers the plan cites, so a reviewer can look the rule up instead of arguing about it. Nothing is quoted unless it genuinely applies to the point it is attached to.

Surfaces and the UI model decide this first

Not a topic in its own right here — a signpost. Which UI model a screen uses (Compose, XML/Views, both, mid-migration, or something in-house) is settled in the workflow above, and it decides which UI rules apply. This section points there and deliberately repeats none of it, so the two can never disagree.

Module and dependency impact blast radius

What the change actually touches, and whether it bends the project's own dependency rules. Read as widely as needed; report at module level, never as a file-by-file transcript.

  1. No new circular dependency — two classes or modules must not end up depending on each other. AND-ARCH-DEPS-2
  2. No inverted layer dependency — a lower layer never reaches upward into a higher one. AND-ARCH-DEPS-1
  3. No new module, and no new edge between existing modules, without it being approved in the design. AND-ARCH-MODULE-3
  4. A new third-party library is an open decision, never a silent addition — declared the way the project declares dependencies, justified against what already exists with its size noted, and pinned to a version when it touches auth, crypto, storage or networking. AND-REL-DEP-1-2-3
  5. Build configuration follows the existing variant and flavour structure, environment values come through the mechanism already in place rather than being hardcoded per call site, and the SDK levels — minSdk, targetSdk, compileSdk — are never moved as a side effect of a feature. AND-REL-VARIANT-1-2-3

State and data flow who owns the truth

Who holds each piece of state, how it changes, and how the screen finds out. Described in the project's own vocabulary — if there is no ViewModel layer, the plan describes what the project actually uses instead of inventing one.

  1. State ownership — one owner per piece of state, following the project's existing state convention rather than a newly invented one, with a single source of truth so two holders cannot drift apart. AND-VM-STATE-1-3
  2. State shape — loading, success, empty and error spelled out explicitly, not left implied. AND-VM-STATE-2
  3. Immutability — a new state object is emitted rather than mutating one the UI is already holding, where that is the existing convention. AND-VM-STATE-4
  4. Event flow — how user actions reach the state owner, and how one-shot effects (navigation, a toast, a dialog) are delivered exactly once and not replayed. AND-VM-EVENT-1
  5. The path end to end — input to state holder to repository to data source and back, naming the real classes involved.
  6. Framework independence — no Android UI type is held in a place the project deliberately keeps them out of. AND-VM-LIFECYCLE-1

Lifecycle, process recreation and concurrency rotation, background, kill

What happens when the screen rotates, the user backgrounds the app, or Android kills the process — and what work runs where.

  1. Lifecycle ownership — which lifecycle owns each piece of work, and how the feature behaves across a configuration change and backgrounding. AND-VM-LIFECYCLE-1-2
  2. Lifecycle-aware collection — UI state is observed in a way that stops when the screen is not visible, not by a raw unscoped collector. AND-VM-LIFECYCLE-3
  3. Surviving process death — decided per piece of state: throwaway, restorable, or genuinely persisted. This is stated even when the answer is “nothing needs to survive” — leaving it silent is a common defect. AND-VM-LIFECYCLE-2
  4. Concurrency — what runs off the main thread and on which dispatcher, following the project's existing injection convention. AND-KT-COROUTINE-1-2AND-PERF-THREAD-1
  5. Cancellation and scoping — which scope owns each operation and what cancels it when the user walks away, with a blocking call switching thread itself rather than relying on every caller to remember. AND-KT-COROUTINE-3-4
  6. Background work — when work must outlive the screen, use the mechanism the project already has, judged against four questions: must it survive process death, can it be deferred, is it user-visible, is it time-critical. A new background mechanism is not introduced when an existing one fits.

Navigation getting there and back

Planned against whatever navigation the project already has — including a fully custom one. Back-stack behaviour is a requirement of any implementation, not a feature of a particular library.

  1. One mechanism only — never a second navigation system running in parallel with the existing one. AND-NAV-DEST-1
  2. Reuse destinations and helpers — a screen that already exists does not get a second route added for it. AND-NAV-DEST-2-3
  3. Arguments and deep links — passed through the typed argument mechanism rather than smuggled through shared global state, validated when they arrive from outside the app, and kept small: a large object is passed by id and re-resolved, not pushed through the back stack. AND-NAV-ARGS-1-2-3SEC-DEEPLINK-1-2
  4. Back-stack behaviour — where the user actually lands on back and on up, stated rather than left to a default that contradicts it. AND-NAV-STACK-1
  5. Navigation fires from a safe point — in response to a real event, guarded so a double tap cannot navigate twice. AND-NAV-STACK-2
  6. Navigation is never triggered from the data or domain layer — screens decide where to go, not repositories. AND-NAV-LAYER-1

Persistence what gets stored

Which existing store handles this kind of data, and what happens to data that is already on the device.

  1. Use the store the project already has for the kind of data involved — no second store for data an existing one already covers. AND-DATA-STORE-1-2-3
  2. Schema migrations are planned explicitly — a schema change ships with its migration, real user data is never wiped to avoid writing one, and the migration is tested where the project tests them. AND-DATA-MIGRATE-1-2-3
  3. Disk work stays off the main thread — reads and writes never block the UI. AND-DATA-THREAD-1
  4. Cache invalidation and the source of truth are defined — what is authoritative, and when the cached copy stops being trusted. AND-DATA-CACHE-1
  5. Sensitive data goes to the project's secure storage, never to ordinary preferences or a plain file. AND-DATA-SEC-1-2-3SEC-STORAGE-1-2

Networking talking to the backend

How the feature calls the server, and what it does when the call fails. A feature resting on an unconfirmed backend contract is recorded as a blocking open question, not planned around.

  1. The existing client, with its existing cross-cutting setup — no ad-hoc HTTP client per feature. AND-NET-CLIENT-1-2-3
  2. The API contract is followed exactly — an endpoint, a field, or a response shape is never invented to make the plan work. AND-NET-CONTRACT-1-2
  3. Transport models stay separate from domain models, mapped the way the project already maps them. AND-NET-DTO-1-2
  4. Authentication is planned — the token is attached centrally rather than per call and never in a URL, and expiry goes through the project's one refresh-and-retry path instead of fanning out to every caller. AND-NET-AUTH-1-2SEC-AUTH-1
  5. Errors, timeouts, retries and offline behaviour are specified — one normalized error shape, with “no connection” told apart from “the server said no” so the screen can offer the right thing, and a cancelled request actually cancelled. AND-NET-ERR-1-2-3-4-5

Testing what will be proven

What gets tested and at which level, matched to the setup the project already has. If a layer has no test infrastructure at all, that is said plainly and raised as an open question — tests that cannot run are never quietly planned, and building a test framework is never smuggled into an unrelated feature.

  1. Match the existing setup — no new test framework introduced as part of a feature. AND-TEST-UNIT-2
  2. Business and domain logic, including the failure and edge paths the design actually defines. AND-TEST-UNIT-1
  3. Determinism — time and dispatchers are controlled so a test cannot pass or fail by luck. AND-TEST-UNIT-3
  4. State-holder behaviour — not just the final value but the sequence emitted along the way, loading through to success or error, with one-shot events asserted to fire once and not be re-delivered. AND-TEST-VM-1-2-3
  5. Instrumentation and UI tests — where the project already uses them. AND-TEST-INSTR-1AND-TEST-COMPOSE-1-2
  6. Translation and RTL checks — every new screen walked through in both a left-to-right and a right-to-left locale, gestures and carousels included, not just the static layout. I18N-TEST-1-2

Performance this feature's real risks

The risks this feature actually carries, not a recited generic list. A risk that needs measuring is labelled as needing measuring — a guess is never written down as a confirmed finding.

  1. Main-thread work — anything heavy enough to make the UI stutter, moved off the main thread. AND-PERF-THREAD-1-2-3
  2. Lists — rendering cost, stable item identity, and whether a large collection needs a recycling or lazy container at all. AND-PERF-LIST-1-2-3
  3. Images — loading, sizing, and not decoding something far larger than the space it is drawn into. AND-PERF-IMAGE-1-2-3
  4. Leaks and retention — a screen or context held by something longer-lived, a listener or collector never unregistered, allocations in a per-frame path, and temporary files left behind. AND-PERF-MEM-1-2-3-4
  5. Startup, download size and battery — the costs a feature adds to the whole app rather than to its own screen. AND-PERF-SIZE-1-2-3

Security nothing leaks

The security section exists so a new feature does not open a way in or a way out. Four things get checked every time — what the app knows, how it talks, what the outside world can reach, and what ends up written down.

  1. Secrets and tokens — no API key, token, password or signing credential in source, and anything baked into the shipped build is treated as public, because a build artifact can be taken apart. SEC-SECRETS-1-2
  2. Transport security — encrypted connections with no cleartext exception, and certificate pinning where the endpoint carries authentication or sensitive data. SEC-NET-1-2
  3. Intents and deep links — a link target is checked against an allowlist before anything navigates to it, and a verified app link is preferred over an unverified custom URL scheme. SEC-DEEPLINK-1-3
  4. Permissions — every new one is justified by a real feature need in the same change, and scoped as narrowly as the platform allows. SEC-PERMS-1-2
  5. WebView surfaces — only where one exists: origins restricted to a known allowlist, and file-system or cross-origin file access left off unless there is a documented need. SEC-WEBVIEW-1-2
  6. Nothing sensitive is written down — no personal data, secret, token, or request or response body reaches a log or a debug-inspection channel. SEC-LOG-1AND-LOG-PII-1

Accessibility usable by everyone

What the feature owes a user who navigates by screen reader, by keyboard or remote, or with the system font turned up.

  1. Roles and labels — every control carries a role matching its function, and a label describing the action rather than the icon: “Delete item”, not “trash icon”. A11Y-ROLES-1-2
  2. Screen-reader support and focus order — the flow is walked through manually with TalkBack, and the reading order follows the visual order, with modals keeping focus inside themselves. A11Y-SR-1-2
  3. Font scaling — text respects the system font-scale setting, and the layout is checked at large sizes without clipping or overlapping. A11Y-FONT-1-2
  4. Activation targets — anything interactive meets the platform minimum, with enough separation from its neighbour to avoid the wrong tap. A11Y-TOUCH-1-2
  5. On a TV screen the target rule changes shape — a reliably focusable element with a clearly visible focus state replaces a touch-target size, because nobody is touching the screen.

Localization and RTL every language

Whether the feature survives being translated, and being mirrored right-to-left.

  1. No hardcoded user-visible strings — every piece of copy comes from a resource, not from the code. I18N-COPY-1AND-UI-RES-1
  2. Dates, numbers and currency are formatted, not assembled — locale-aware formatters decide the shape, including the currency symbol and the grouping and decimal separators, rather than string concatenation. I18N-FMT-1-2
  3. RTL layout and mirroring — spacing and alignment are direction-relative rather than left and right, order comes from the resolved direction, and directional icons are flipped explicitly, because mirroring the layout does not flip icon content on its own. I18N-RTL-1-2-3-4

Logging and analytics what gets recorded

Reuse the project's conventions, record only what the feature genuinely needs, and keep it clean of anything personal.

  1. The existing logging abstraction is used — the project's logger, not raw log calls scattered through new code. AND-LOG-HYGIENE-1
  2. Debug logging is gated — it does not run in a release build, and it is easy to strip. AND-LOG-HYGIENE-2
  3. Errors are never silently swallowed — enough non-sensitive context survives to investigate a failure, rather than an empty catch. AND-LOG-HYGIENE-3
  4. Analytics events are the ones the design specifies — through the existing wrapper, reusing names that already exist, and firing once per real user action rather than again on every recomposition or rotation. AND-LOG-ANALYTICS-1-2-3
  5. No personal data anywhere downstream — not in analytics properties, and not in crash-reporter breadcrumbs, which get checked and redacted. AND-LOG-PII-2-3

Inside output-contracts.md

The full analysis is produced every time. What differs is which parts of it are handed over, and where they land. Nothing is assumed to be pasted in verbatim.

The five parts of the analysis

  1. Implementation model found. What the repository actually does today — UI model per screen, architecture, state, navigation, DI, concurrency, networking, persistence, module layout, and the TV model when it is a TV feature. Every line labelled with the file that proves it, or marked as reused, inferred, or unknown. Produced in full every time, because everything else rests on it.
  2. Technical approach. The plan itself, broken down by the domains in the previous section, each item citing the rules it follows.
  3. Impacted modules. The change inventory — what gets touched, as opposed to where the new code goes. Resolution rules below.
  4. Existing · required · recommended. Three lists that are never merged: what is already there and will be followed, what this feature genuinely needs, and deviations being recommended — each with a justification and an approval gate. Optional modernisation is routed into the recommended list, never into required work.
  5. Unresolved decisions. Every question that needs a human answer, with the options and what each one implies.

How precisely impacted modules are reported

The most common failure here is a design document that quietly becomes a task list. Four rules stop that.

  1. Report at module and change-class level — name each affected module, package, component or service, say what class of change it undergoes, and whether it is created, modified, or only read.
  2. Give an approximate site count when one change repeats — “all player construction sites move to the builder API, roughly forty sites” carries the scale without listing forty files.
  3. List individual files only when the set is small — about ten or fewer for a given change — or when a specific file is a genuine boundary: it defines a public surface, carries a decision of its own, or is the seam the design turns on.
  4. Every path is one that was actually seen. Where a location genuinely is not decided yet, it is marked unknown rather than filled in with something plausible.

Per-file expansion belongs to the task breakdown, which re-reads the repository to do it. A design that lists every touched file has written the task breakdown in the wrong document.

Traceability

Every element of a plan points at something concrete: a repository claim points at a file path, a requirement points at the upstream document section it came from, a rule points at a real identifier that genuinely applies, and a recommendation points at its justification. A rule that is merely adjacent to the point being made is not cited at all.

Inside tv-context.md

Read only when the feature is confirmed as a TV feature. TV is a context signal inside the Android platform — there is no separate TV platform, agent, skill or command.

The governing assumption: an Android TV app may be built any way at all — standard TV frameworks, an in-house framework, or something else entirely. Find out which before making a single decision. Leanback, Compose for TV, or any standard component set is never assumed.

The discovery pass — run before proposing anything

Ten things to establish, each recorded with the evidence for it, or marked unknown.

  1. Focus handling — how focus moves, is tracked and restored, and whether there is a custom focus engine.
  2. D-pad and remote input — where key events arrive and get dispatched, plus any media or remote-button handling.
  3. Navigation — the TV navigation mechanism, which may be different from the mobile one in the very same repository.
  4. TV UI components — what is actually used: framework widgets, Compose for TV, Leanback widgets, or in-house components.
  5. Playback integration — the player, who owns its lifecycle, how the surface is handled, and the playback-state model, where the feature touches playback.
  6. Lifecycle conventions — TV-specific screen lifecycle handling, including background and resume behaviour.
  7. Reusable base classes — TV base activities, fragments, screens or wrappers the feature should extend.
  8. In-house framework modules — which exist, and what their public surface is.
  9. Launcher and banner configuration — the manifest entries that make this app a TV app.
  10. Packaging and release configuration — TV-specific variants, flavours, or distribution setup.

The one thing that is true regardless of toolkit

A TV app declares itself in the manifest whichever way its UI is built — a launcher activity carrying the TV launcher intent category, touchscreen declared as not required, a leanback feature declaration whose required flag decides TV-only versus shared with mobile, and a banner on the application element, localized. These facts confirm a TV target and say nothing whatsoever about the UI framework. The names carry the word “leanback”, but they are platform and store-filtering identifiers rather than a library dependency — they remain current even though the Leanback library itself is now deprecated, and they apply equally to a Compose-for-TV or fully custom app. Equally toolkit-independent: D-pad traversal, an always-visible focus indicator, and predictable back behaviour are expectations of every TV implementation.

TV planning rules

  1. Never propose a migration to Leanback, Compose for TV, or anything else, unless the feature explicitly asks for it and it is approved.
  2. Never carry a touch assumption across. Touch targets, taps, swipes, scroll affordances and soft-keyboard flows do not transfer to a remote control.
  3. Reuse the existing custom components wherever they already cover the need.
  4. Name weaknesses without redesigning around them. Identifying a gap or a risk in the existing model is in scope; unilaterally re-architecting is not.
  5. Where a repository has both mobile and TV surfaces, plan only for the confirmed one, and never assume the mobile conventions apply to the TV side.
  6. If the TV model cannot be identified from evidence, stop and report it rather than planning against an assumed one.

Scope boundary. This file's job is discovery and respect for what exists. It does not author TV standards — that is ANDROID-003. Until those rules exist, a TV rule identifier that has not been written is not cited; the gap gets named instead.
