# QA bug consumer contract (Dev side)

How the Dev Plugin reads one QA bug, in `scripts/bug-intake.ts`. This is the Dev Plugin's
**consumer-side** copy of a contract QA owns. It is pinned to what QA's helper writes as of
ono-plugin-qa `origin/main` `8d8ed99` (QA Plugin v0.8.0), meaning `renderBugMarkdown` in
`scripts/lib/qa-ledger/bugs.mjs` and the ledger records in `scripts/lib/qa-ledger/model.mjs`.
The Dev Plugin never writes to a QA repository; QA owns every file named here.

## Two sources, each read for what it is authoritative on

| Source | What Dev reads from it | Verified how |
|---|---|---|
| `qa-ledger/` (ledger.json, `qa-ledger/scopes/bug/<id>.jsonl`, `runs/*.jsonl`, `builds/*.json`) | the bug's **recorded facts**: report (title, steps, expected, actual, origin, found-in build, description), folded context (title, surfaces, severity, capability, external ref, linked cases, related scopes), runs that reference the bug, builds that claim its fix, re-test evidence | every record's `hash` re-computed (`sha256(canonical(record − hash))`) and every stream's `prev` chain checked; `qa_ledger_schema` must be `1` |
| `bugs/<id>/bug.md` | the bug's **derived state** and history: State, Next action, Fix under test, Pending re-test surfaces, Fixed in build, Found in build, Fix Claims (with outcomes), Reproduction History, Re-test History | parsed against the fixed shape below, then cross-checked against the ledger |

QA bug state is never persisted in the ledger. It is derived by replaying the bug's
streams, and QA's own derivation (`deriveBug`) is the single source of truth. Dev does not
re-implement that replay, which would be a second copy that drifts. It reads the result QA
already rendered.

## The view's contracted shape

- Line 1: `# <id> — <title>`.
- One `| Field | Value |` table, with exactly these rows in this order: Bug, State, Next
  action, Severity, Origin, Affected surfaces, Found in build, Fix under test, Pending re-test
  surfaces, Fixed in build, Resolution, External reference, Assignee, Capability, Reported.
- Exactly these `## ` sections, in this order: Summary, Reproduction Steps, Devices, Linked
  Test Cases, Related Scopes, Fix Claims, Reproduction History, Re-test History, Evidence,
  History.
- Reproduction Steps: numbered steps, then `**Expected:** …` and `**Actual:** …`.
- Tables (with these headers exactly):
  - Fix Claims: `Build | Claimed at | Outcome`
  - Reproduction History: `Run | Build | Surface | Device | Outcome | At | Notes`
  - Re-test History: `Run | Build | Fix build | Surface | Device | Outcome | At | Notes`
- An empty table renders `None.`; an empty cell renders `—`; a `|` inside a cell is `\|`.
- State is one of: `new`, `verification_blocked`, `assigned`, `fix_delivered`, `reopened`,
  `closed_verified`, `closed_not_reproducible`, `closed_duplicate`, `closed_wont_fix`.

Any deviation is refused as `QA_VIEW_CONTRACT`; the reader never guesses at a shape it does
not know.

## Staleness cross-check

The view is regenerated by QA's helper on every bug write, but nothing stops a stale or
hand-edited copy. Before using the view, the reader requires it to agree with the verified
ledger on:

- the bug ref, title, steps, expected, actual, severity, affected surfaces, external ref and
  capability;
- found-in build, when the report recorded one;
- the set of reproduction run ids and re-test run ids (closed runs whose `bug_ref` is the bug);
- the set of fix-claim builds (builds whose `fixes_claimed` includes the bug).

A disagreement is `QA_VIEW_STALE`, together with the fields that disagree and QA's
regeneration command (`qa-ledger.mjs bug render --bug bug:<id>`).

## What Dev does with the state

| QA state | intake status | Dev may start |
|---|---|---|
| `assigned` | `ready_for_dev` | yes |
| `reopened` | `reopened` (the failed cycle's evidence is returned) | yes, as the next cycle of the same bug |
| `fix_delivered` | `awaiting_qa_retest` | no; QA re-tests first |
| `new`, `verification_blocked` | `needs_qa_verification` | no; QA verifies first |
| `closed_*` | `closed` | no |

Dev never moves a QA state. It reports the state and refuses to start where QA still owns
the next step.

## Limitations

- **Derived view.** QA's view says it is "a derived view, never read back", which is about
  QA itself. Dev reading it is a consumer relying on a rendering. The cross-check makes
  staleness detectable, but derived fields the ledger cannot confirm without replaying
  QA's state machine (State, Next action, the outcome of each fix claim, Pending re-test
  surfaces) are trusted as QA rendered them.
- **Rendering drift.** When QA changes `renderBugMarkdown`, the reader refuses
  (`QA_VIEW_CONTRACT`) rather than misreads. Re-pinning this contract is then a deliberate
  Dev change.
- **Recommended QA follow-up.** A machine-readable bug view, such as JSON or frontmatter
  carrying `state` and the ledger head hash it was derived from, would let Dev check
  freshness exactly and stop parsing Markdown. Until QA ships one, this contract stands.
