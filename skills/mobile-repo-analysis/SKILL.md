## Methodology

1. **Resolve canonical repository knowledge, then detect the platform.** Apply the `repo-knowledge-consumer` skill first, so what the repository already knows about itself is in hand before anything is re-derived. Then run `repo-analyst`'s platform-detection algorithm in full (raw signal checks → RN/iOS/Android/React verdicts → RN-native-shell linkage check → final routing) — see `agents/repo-analyst.md`. Platform detection always runs regardless of what the manifest contains; `stack.platformHints` is advisory corroboration, never a substitute. If monorepo tooling is present, run detection per touched workspace/package, not once for the whole repo. When no canonical knowledge is available, this step behaves exactly as it always has.

2. **Present the detected context to the user and require confirmation before treating it as authoritative — always, even at high confidence.** Detection is a recommendation. Show the detected `platform` and `device_type` and ask the user to confirm ("Yes, continue") or select another context. The confirmed context must resolve to **exactly one** platform (`react-native` / `react` / `ios` / `android`) and **exactly one** device type (`mobile` / `tv`); on rejection, have the user select from those values and validate them (reject empty/invalid and re-ask). **If detection returns multiple platforms or a mixed repository state, do not offer a "continue with mixed" path — present the candidates and require the user to select the single active platform and device type for the current feature.** There is no `mixed` authoritative platform and no `mixed` device type; never guess a default. The user-confirmed values become authoritative for this feature and are what get written to frontmatter.

3. **Once platform is confirmed, fill only the gaps in the stack picture.** Split this into what can be reused and what must always be derived:

   - **Reuse the neutral stack inventory when available.** If `conventions` is in `usableCategories`, read `docs/project/patterns.md` for the navigation library, state-management library, data-fetching layer, test runner, monorepo/workspace tooling, and lint/format tooling, and cite the sections used. Do not re-enumerate `package.json` for facts that document already states. Only when `conventions` is in `deriveLive` do you detect these yourself — and then detect, never assume.
   - **Carry the component inventory pointer forward when available.** If `inventory` is in `usableCategories`, `repo-analyst` reports that `docs/project/components.md` is reusable (via the Repository Knowledge section) rather than inventorying components itself — reading it and reusing existing screens, components, and hooks instead of proposing duplicates is the invoked architect's job. This is the single highest-value reuse in the pipeline: that document exists specifically to be read before speccing a feature.
   - **Always run the standards-conformance comparison.** Scan the folder structure against `standards/react-native/rn-architecture.md`'s expected layering (`ARCH-LAYERS-*`, `ARCH-FOLDERS-*`) regardless of what was reused. `patterns.md` states what the conventions are; it does not judge them against Ono's standards, and that judgment is this plugin's job.
   - For iOS and Android: lightweight existence checks only — **deliberately so**, because `ios-architect` and `android-architect` each run their own deeper platform inspection (their dev-planning skills' §3) rather than relying on this step. For React (web): lightweight existence checks only **for now** — deep convention detection is deferred until `standards/react/*` is authored. See `agents/repo-analyst.md`.
   - **Always resolve the device type for this workflow** — exactly one of `mobile` or `tv` (the mobile-vs-TV context signal, not a new platform value, with no `mixed` value) — using `repo-analyst`'s device-type markers (tvOS device family / `TVUIKit`, Android Leanback, `react-native-tvos`, Tizen/webOS packaging). The manifest carries no device information, so this is never reused. If a repo has both targets, resolve the one this feature is about, asking the human when unclear.

4. **Hand the full structured findings summary — all five sections, in the order `repo-analyst` produces them (Repository Knowledge, Platform Detection, Device Type, Stack Detection, Standards Conformance) — to the matching platform architect agent(s)** — `rn-architect`/`ios-architect`/`android-architect`/`react-architect`. Hand them to **exactly one** architect: the one matching the single platform the user confirmed in step 2. There is no `mixed` authoritative platform, so a feature is never split across several architects.

5. **Resolve the design reference before proposing any UI.** A design reference is required **only** when the feature introduces or changes user-facing UI — and is **mandatory** when it does.
   - **No new or changed user-facing UI** (technical migration, refactor, dependency upgrade, infrastructure work, performance improvement, other behavior-preserving change) → do not ask for Figma or any other design input. Record `design_reference_status: not_required`, `design_reference_type: none`, `design_reference: null`, `figma_link: null`.
   - **New or changed user-facing UI** → one supported reference is mandatory: a Figma link (`figma`), a design specification document (`document`), exported mockups/screenshots (`screenshots`), a Zeplin/Adobe XD or other approved artifact (`other`), or a precisely named existing screen/component to mirror (`existing_ui`). If none was supplied, **stop and ask for one and wait** — do not proceed on an assertion that no design exists, do not fall back to `not_required`, and never guess layout from prose. Record `design_reference_status: provided` with the matching `design_reference_type`, putting a Figma URL in `figma_link` and any other reference in `design_reference`.
   - Read the reference through the mechanism that fits its type: the `figma` MCP server for `figma`, the file/URL for a document or exported mockups, the existing implementation in this repo for `existing_ui`. If it cannot be accessed, **stop with the exact error.** Figma is one supported type, not a requirement.

6. **The one invoked architect proposes an approach** (screens/views, state/data, navigation/routing, folder placement) citing that platform's standard IDs, grounded strictly in what was detected and (for UI) the resolved design reference.

7. **Populate `templates/feature-analysis-template.md`** with the feature request; the confirmed `platform` (a single value — never `mixed`) and the confirmed `device_type` (`mobile`/`tv`) frontmatter fields; the six `repo_knowledge_*` frontmatter fields and the `## Repo Knowledge Reference` section, per the `repo-knowledge-consumer` skill's Step 6 block shape; `repo-analyst`'s findings in `## Repo Context` — **cite reused knowledge, embed only what was derived live**: Platform Detection, Device Type, and Standards Conformance are always derived live and so always embedded, while each Stack Detection entry is individually tagged `[reused: <path>#<anchor>]` or `[derived live]`; the four design-reference fields resolved in step 5 (`design_reference_status`, `design_reference_type`, `design_reference`, `figma_link`); and the proposed approach as a single flat "Proposed Technical Approach" section for the confirmed platform. Leave `status: proposed` for a human to review and approve.
