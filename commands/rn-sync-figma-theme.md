Read the Figma design system at `$ARGUMENTS` and generate or update this React Native repo's NativeWind theme from its variables — colors, spacing, radius, and typography (font family, size, weight, line height).

**This is a standalone utility, not part of the eight-stage feature pipeline.** It produces no feature analysis, DD, or task breakdown. See the `rn-nativewind-theme-sync` skill's [Approval model](../skills/rn-nativewind-theme-sync/SKILL.md#approval-model): this command bypasses **feature-pipeline approval** only — it never bypasses the repository write hooks (`require-approval-before-code`, `block-main-branch-changes`, `protect-secrets`) or the semantic confirmation gates that run whenever an existing token value would change or two incoming Figma values collide.

1. **Resolve `TARGET_ROOT`** the same way every other command does — do not assume the current working directory.
2. **Confirm the platform is `react-native` — alert and hard-fail otherwise.** Apply the `rn-nativewind-theme-sync` skill's Step 0 platform gate (`scripts/figma-theme-tokens.ts detect-platform`): if `TARGET_ROOT` is not detected as React Native, **stop immediately with an explicit alert** stating the detected platform (or that none was detected) and that no Figma data was read and no files were changed. This is a hard failure (`status: "failed"`), not a question — do not fall through to another platform and do not continue to the NativeWind readiness gate.
3. **Require a Figma URL in `$ARGUMENTS`.** If missing or malformed, stop and ask for one — do not reuse a Figma link recorded elsewhere for an unrelated feature.
4. **Detect `--dry-run`** in `$ARGUMENTS`. When present, the run executes every read-only state through `DIFF_COMPUTED` (and still shows the override-confirmation table if one is needed) but never writes a file. Prefer `--dry-run` as the default way to preview a large or unfamiliar sync before committing to it.
5. **Apply the `rn-nativewind-theme-sync` skill in full**, following its explicit workflow states end to end: `INIT → PLATFORM_VERIFIED → INPUT_VERIFIED → FIGMA_SCOPE_RESOLVED → VARIABLES_READ → VARIABLES_RESOLVED → TOKENS_CLASSIFIED → TOKENS_NORMALIZED → TARGET_RESOLVED → DIFF_COMPUTED → CONFIRMATION_REQUIRED → WRITE → VERIFY → REPORT` (or `CANCELLED` at the confirmation gate). Never advance past a state whose invariant failed — stop and report exactly which one.
6. **Surface every MUST-ASK point the skill raises** — NativeWind absent, an ambiguous design-system scope (including a linked mockup page vs. the actual design-system page), an ambiguous mode assignment, a naming collision, more than one plausible canonical token source, a pending token override, ambiguous mode-baking on NativeWind v2/v3 — rather than picking a default on the user's behalf. Two things that look similar are not MUST-ASK: non-React-Native platform is Step 2's hard failure, not a question (never ask "continue anyway?", just stop); and an unresolved alias or a genuinely unclassified variable (the skill's NEITHER category) is excluded and reported, not asked about, unless it leaves nothing else in the run to write. Never ask about a MAY-DECIDE case (formatting, ordering, whitespace, deterministic normalization) — the skill's script already decided those.
7. **After a real (non-dry-run) write, require the skill's Step 11 verification to pass** before reporting success — re-reading the file and confirming it matches the approved Token IR exactly, with no unapproved override and no unrelated region touched.
8. **Report back** both the skill's human-readable summary (source, scope, counts, changed tokens, overrides, warnings, files changed, required follow-ups) and its machine-readable result (`status`, `platform`, `figmaScope`, `counts`, `filesChanged`, `warnings` — see the skill's Step 13). `status` is one of `success`, `needs_confirmation`, `blocked`, `cancelled`, `failed` — report it verbatim, don't paraphrase it into a different word.
