# React Smart TV Standards

## Purpose & Scope

These standards apply to React (web) code running on a **Smart TV** surface — a Samsung Tizen or LG webOS TV web application, a vendor browser-based TV runtime, or a browser build driven by a remote — reviewed by `react-code-reviewer` and `react-performance-reviewer`, planned by `react-architect`, implemented by `react-feature-developer`. Each rule carries a stable `REACT-TV-*` ID. A baseline, not exhaustive.

**Smart TV is `device_type: tv` inside the React platform, never a platform of its own.** No `react-tv` platform value, no `mixed` device type, no TV-specific agent, skill, or command.

This document inherits the **React lane conventions** in `react-coding-standards.md` — the repository-first hierarchy (a repo's established TV model outranks these rules; vendor docs are rank-5 supporting only; absence of a convention is not compliance), technology-neutrality, the no-modernization-aside stance, the `REACT-` prefix, and the `## External references` pattern. Findings are limited to code introduced or modified in the reviewed scope.

**Every `REACT-*` family still applies on a TV surface.** This document adds obligations and names TV equivalents where a base rule assumes a pointer; it never relaxes or forks one.

> **Additive.** Authored after the REACT-001 freeze (2026-08-16); defines a new root and renumbers nothing.

## Lane ownership

The React lane routes by the cited ID's own root. A standalone `REACT-TV-*` root does not resolve that way, so its routing is stated here and nowhere else authoritatively — other documents point here rather than restating it.

| Family | Filed by | Reachable at |
|---|---|---|
| `REACT-TV-FOCUS-*`, `REACT-TV-INPUT-*`, `REACT-TV-UI-*`, `REACT-TV-MEDIA-*`, `REACT-TV-LIFECYCLE-*`, `REACT-TV-API-*`, `REACT-TV-PKG-*` | `react-code-reviewer` | see *Stages* |
| `REACT-TV-PERF-*` | `react-performance-reviewer` | Diff · Release |

- **`REACT-TV-PERF-*` is the performance reviewer's; every other TV family is the code reviewer's.** This holds when a concern *sounds* performance-adjacent: a focus-restoration bug that feels sluggish is `REACT-TV-FOCUS-*`.
- **`REACT-TV-PKG-5`/`-6` are filed by the React code reviewer, not the security lane.** They cite `SEC-SECRETS-*`/`SEC-HARDEN-*` as supporting rules. *Recorded divergence:* the shared `mobile-security-reviewer` has no TV awareness — it is never told a vendor manifest, keystore, `.wgt` or `.ipk` exists — so routing these to it would leave a committed signing certificate filable by nobody. Wiring the security lane for TV is a **cross-lane gap logged for that lane's owner**; until then these two rules stay here so they have an owner. Application-code security remains entirely the security lane's.

### Stages

A rule is only citable in a scope that can reach it. **Where the scope cannot reach a rule, record it Not Applicable with the reason — never as passed, never as a finding.**

| `REACT-TV-API-1`/`-3`, `REACT-TV-UI-1`/`-4`, `REACT-TV-INPUT-5`, `REACT-TV-PERF-1` | **Design** — each depends on a platform fact or a stated budget established while planning. At Diff, cite only against a change that *contradicts* an established decision, or file the absence per *Unestablished facts* below. |
| `REACT-TV-API-2`/`-4`, `REACT-TV-INPUT-8` | **Design · Diff** |
| `REACT-TV-UI-7` | **QA / implementation** — requires running the platform's assistive technology on a device. At Diff only the semantic half is reachable (roles, labels, states, focus order); the walkthrough becomes a stated QA-handoff item. |
| `REACT-TV-PKG-*` | **Diff, when packaging config is in the reviewed scope** — a `config.xml`, `appinfo.json`, packaging script, or env/target config **in the diff** is reachable and reviewed. Absent from the diff, the family is N/A. |

**Release-stage note (honest gap).** These rules have **no release-stage enforcement point today.** The shared release chain — `/prepare-mobile-release`, `mobile-release-readiness`, `mobile-release-engineer`, `release-checklist-template.md` — has no TV awareness, and invokes only `react-performance-reviewer` for React. So `REACT-TV-PKG-*` is enforceable **only** when packaging config appears in a reviewed diff. Adding a TV branch to the release chain (under shared `REL-NATIVECONFIG-*`, `REL-VERSION-*`, `REL-ENV-*`, `REL-STORE-1`) is a **cross-lane gap logged for the release lane's owner**. Do not record these rules as verified at release; the stage does not check them.

### Unestablished facts

Several rules depend on a per-platform, per-firmware vendor fact (cookie viability, cross-origin model, safe-area inset, text-scale support, which keys require registration, required manifest fields). External references are **not fetched at review time**, so at Diff stage an agent generally cannot establish such a fact itself. It must not invent one, and must not treat the gap as a pass. The finding is:

> *the repository does not record the platform fact this rule depends on* — filed against the change that assumes one, naming the rule and the vendor page to consult.

At **Design** stage the prohibition does not apply: consulting vendor documentation is part of planning, and the established fact is recorded in the design with its source.

### Missing conventions

Many rules below are phrased against "the repository's existing" TV convention. Resolve an absence in this order, never by supplying a preference:

1. **The convention exists** → follow it (rank 2); it outranks these rules.
2. **No TV surface exists yet (greenfield)** → the focus model, key map, safe-area inset, and budget are **required feature-specific extensions**, proposed once at app level as an approval-gated decision — not per feature, and not a migration. Absence is a gap to fill, not an ambiguity to stop on.
3. **A TV surface exists but its convention cannot be determined** → mark `[unknown]`, record it as an unresolved decision, and cap any related finding at Minor. Do not assert a verdict from a diff.

### One defect, one finding

**File what your lane sees; never suppress an observation assuming the other reviewer will file it** — the two reviewers cannot see each other's live output, so silence is not coordination. Where one defect satisfies several rules, file once under the **owning ID**, citing the others inside it.

**Precedence: the row naming the more specific *mechanism* wins over the row naming the *symptom*.**

| Defect | Owning ID | Cited inside |
|---|---|---|
| Player left undisposed on unmount or source change | `REACT-TV-MEDIA-3` | `REACT-TV-PERF-2`, `REACT-FC-5` |
| Key or lifecycle listener left without cleanup | `REACT-FC-5` | `REACT-TV-INPUT-3`, `REACT-TV-LIFECYCLE-1` |
| Memory retained on navigating away — **other than an undisposed player or listener (rows above)** | `REACT-TV-PERF-2` | `REACT-TV-PERF-3` |
| Full-resolution asset decoded for a small display context | `REACT-TV-PERF-3` | `REACT-PERF-IMAGE-1` |
| Long rail not virtualized at all | `REACT-PERF-LIST-1` | `REACT-TV-PERF-3` |
| Rendered-window strategy unmounts the focused row | `REACT-TV-UI-6` | `REACT-PERF-LIST-1`, `REACT-TV-FOCUS-1` |
| Timers, polling, or subscriptions left running while backgrounded | `REACT-TV-LIFECYCLE-4` | `REACT-TV-PERF-1`, `REACT-PERF-MAINTHREAD-1` |
| Focus lost or reset after a transition | `REACT-TV-FOCUS-1` | `REACT-TV-FOCUS-4` |

**`react-code-reviewer` performs the deduplication** when it populates the review template, since it is the agent that merges. `react-performance-reviewer` names the owning ID on any finding that appears in this table so the merge can resolve it.

## Applicability: is this a TV surface?

This document applies **only** to a surface that runs on a TV. On a repository with no TV surface it is entirely **N/A** and none of its rules may be raised.

- At **planning and implementation**, `device_type` is read from frontmatter and is authoritative — never re-detected, never defaulted.
- At **review** there is no confirmed `device_type`. Infer from the reviewed files, note it in Scope, do not block to ask. **Where the surface cannot be established, say so once in Not Applicable / Skipped and cite no TV rule.** Do not guess a surface in order to have something to file, and do not treat the uncertainty as a pass — an unestablished surface is `[unknown]`, never `mobile`. Under `[unknown]`, apply the base families but suppress any finding whose **only** basis is a pointer/touch premise (`A11Y-TOUCH-1` sizing, a hover affordance, pointer-derived INP), recording each as N/A — surface unestablished.
- **`device_type` names the feature's primary surface, not the only one that matters.** A component with an established TV consumer carries TV obligations even on a `device_type: mobile` feature — see the shared-component trap.

**Evidence establishing a TV surface** (labelled `[evidence:path]`): a vendor manifest (`config.xml` with a Tizen namespace, `appinfo.json`); a vendor packaging/CLI script; a vendor platform API in source (`window.tizen`, `window.webOS`, `webOSDev`); a spatial-navigation or TV-focus dependency; a TV-only route, entry point, or build target; a TV component folder or screen wrapper.

### TV detection traps

Each names the confident-but-wrong finding it prevents. Prefer the authoritative signal; mark `[unknown]` rather than guess.

- **A TV dependency in `package.json` ≠ a TV surface for this diff.** A repo may ship a phone app and a TV app from shared code; the surface the changed file renders on decides. *Prevents:* filing `REACT-TV-FOCUS-*` against a shared component whose only consumer here is the phone app.
- **A shared component is neither auto-compliant nor auto-exempt.** One used by both surfaces must satisfy both. Since a diff cannot enumerate consumers, and marking every shared change N/A would systematically miss real TV blockers (`outline: none` added to a shared `<Button>`), file a **conditional finding**: cite the rule, state that applicability depends on whether the TV surface renders this component, and name the check (search for the import in the TV entry tree). Bounded tracing of the *changed* component is in scope; repo-wide tracing is not. *Prevents:* both the false pass and the false finding.
- **A runtime `window.tizen` / `window.webOS` guard ≠ the vendor runtime is the target.** Such guards are also written for dev-browser degradation, and pointer events working in a dev browser prove nothing about the shipped surface. Confirm the target from the packaging script or manifest. *Prevents:* "this is a Tizen app" from one guarded reference; accepting a hover-only affordance verified in Chrome.
- **Pointer/hover media queries do not identify a TV.** `pointer`/`hover` describe pointing-device accuracy and hover capability, and a TV may genuinely report either depending on whether a platform cursor mode is active. *Prevents:* keying a layout or affordance decision to the wrong device class.
- **Tizen and webOS differ in manifests, key codes, packaging, lifecycle, and input model.** Neither substitutes for the other, and a repo may target both. *Prevents:* citing one vendor's requirement against the other's app.
- **Resolution does not imply the device.** A 1920×1080 viewport is as likely a desktop browser, and a TV's *graphics* resolution is per-model and manifest-declared, independent of the panel and of video playback. *Prevents:* inferring the device tier or a pixel budget from viewport size.

## Focus & Spatial Navigation

Focus is the primary cursor: on a D-pad-driven surface, losing it strands the user with only Back or Home to recover.

- `REACT-TV-FOCUS-1` **Exactly one element holds focus at all times, and it is never lost.** Every screen, route, modal, and async state has a defined focus target; after any transition, list refresh, or conditional re-render, focus lands on a deliberate element — never a removed or hidden node, never `document.body`.
- `REACT-TV-FOCUS-2` **Focus movement follows the repository's existing focus model** — a spatial-navigation library, a custom engine, the platform's built-in navigation, or explicit key handling, in no order of preference. A second parallel mechanism is never introduced alongside an existing one, and no engine is hand-rolled where one exists. Greenfield: see *Missing conventions*.
- `REACT-TV-FOCUS-3` **The focused element carries a clearly visible focus indicator**, legible at a 10-foot distance rather than a 1px outline or subtle tint, meeting the repository's contrast requirement against its actual background. `outline: none` is never applied without an equally visible replacement. This is how shared `A11Y-TOUCH-1` is satisfied on a TV form factor.
- `REACT-TV-FOCUS-4` **Focus is restored on return, not reset.** Returning to a visited screen, or exiting a modal or player, restores the element the user left — the previous row and item in a grid, not the first cell. Restoration state is placed per `REACT-STATE-BOUNDARY-*` (URL-appropriate state per `REACT-STATE-BOUNDARY-2`).
- `REACT-TV-FOCUS-5` **Focus order matches the visible spatial layout.** Up/Down/Left/Right move to the element actually adjacent on screen, not the next node in DOM order. Where DOM and visual order diverge (a grid, an absolutely positioned rail, a reordered flex container), adjacency is stated explicitly.
- `REACT-TV-FOCUS-6` **Overlays, modals, and dialogs trap focus** while open and release it to the invoking element on close. Letting D-pad focus wander into the obscured content beneath is a defect (shared `A11Y-SR-2`).
- `REACT-TV-FOCUS-7` **Every interactive control is reachable, and non-interactive content is not focusable.** No control is stranded behind an unreachable adjacency; decorative or static content is not inserted into the focus order, and is also hidden from assistive tech per shared `A11Y-ROLES-4`. An element made focusable purely to receive key events, without being an interactive control, is a defect.
- `REACT-TV-FOCUS-8` **Under RTL, focus stays spatial and the mirroring is deliberate.** `REACT-TV-FOCUS-5` governs unchanged: a D-pad press moves to the element **visually adjacent** in that direction, so in a mirrored rail Right lands on the item that is *earlier* in reading order — the remote maps to screen geometry, not reading order. **The filable defect is a container whose focus adjacency and CSS direction derive from different sources** — CSS mirrors while adjacency stays hardcoded LTR, or the reverse. Verified in the bidirectional walkthrough (shared `I18N-TEST-1`, `I18N-TEST-2`); note that `I18N-TEST-2`'s gesture-mirroring expectation does not transfer, because D-pad input direction is not remapped.

## Remote & Key Input

- `REACT-TV-INPUT-1` **Key codes are defined once in a central, named mapping** — never as numeric literals in component code. `if (e.keyCode === 10009)` is a defect; a named constant resolved through one platform-aware key map is the requirement. Values are traceable to the target platform's official key-code reference; where the repository's existing map diverges, record the divergence as an unresolved decision rather than filing against it (rank 2 wins).
- `REACT-TV-INPUT-2` **The key map is per-platform, and application code names only the logical key** (`BACK`, `OK`, `PLAY_PAUSE`). Platforms assign different codes to the same logical key — establish each target's codes from its own reference — so a single table merged across platforms is a defect. Whether the mapping resolves at build time or runtime follows the repository's packaging model (`REACT-TV-PKG-7`).
- `REACT-TV-INPUT-3` **Key handling is scoped to the focused subtree, not attached globally per component.** A component registering its own `window`/`document` `keydown` competes with every other mounted component. Key handling belongs to the focus model (`REACT-TV-FOCUS-2`); a genuinely app-level listener (root Back) is single and owned by one module. Every listener obeys `REACT-FC-5`.
- `REACT-TV-INPUT-4` **Back is handled at every level and always has an effect.** It closes the topmost overlay, navigates up one level, or at the root exits or prompts to exit per the platform's convention — never a no-op, never silently swallowed. Back-driven navigation goes through the router (`REACT-ROUTE-SERVICE-3`), and `REACT-ROUTE-UX-3` applies unchanged. Where the platform drives Back through the History API by default, a repository that opts out owns the behavior itself.
- `REACT-TV-INPUT-5` **Keys the platform gates behind registration are registered before use.** Where a runtime delivers only some hardware keys automatically and requires the app to register interest in the rest (media and colour keys typically), that registration is part of the feature. A handler for an unregistered key is dead code that works on a keyboard and fails on a remote. Which keys are gated is a platform fact — see *Unestablished facts*.
- `REACT-TV-INPUT-6` **The D-pad is the only guaranteed input, so no pointer, hover, or gesture affordance is load-bearing.** Hover-reveal, tap, swipe, drag, long-press, and pointer-scroll may be unavailable; anything reachable only through one of them is unreachable. The D-pad path is primary and a platform cursor mode is additive. Rails and carousels advance by focus movement, not by drag or scrollbar.
- `REACT-TV-INPUT-7` **Where the platform offers a cursor mode, mode transitions are handled and focus is reconciled.** Some TV platforms ship a pointing remote that produces an on-screen cursor and standard mouse events, and signal when the user switches between 5-way and cursor mode. An app on such a platform handles the transition rather than assuming one model: focus remains defined when the cursor appears or disappears (`REACT-TV-FOCUS-1`), and hit targets are large enough to acquire with a wobbling cursor. Whether the target platform has a cursor mode is a platform fact.
- `REACT-TV-INPUT-8` **Text entry accounts for the platform IME.** Focusing a text input raises the platform on-screen keyboard, which takes focus, may resize or overlay the viewport, and fires blur on the input. Focus is restored to a deliberate element when the IME is dismissed (`REACT-TV-FOCUS-4`), layout survives the viewport change, and the feature minimises typed input on a remote-driven surface rather than porting a phone form wholesale.

## 10-Foot UI & Layout

- `REACT-TV-UI-1` **Layout is overscan-safe.** Interactive controls and essential text stay inside a safe-area inset from every edge; full-bleed background imagery may extend to the edge, content may not. The inset is a stated value in one place, not re-guessed per screen, and is expressed against the declared logical viewport (`REACT-TV-UI-3`) — a pixel inset is meaningless without the resolution it applies to. Where the platform publishes an inset, follow it; where it publishes none, the repository states its own convention.
- `REACT-TV-UI-2` **Type, controls, spacing, and separation are sized for a 10-foot viewing distance**, following the repository's TV scale. Phone and desktop type ramps and target sizes are not reused. Adjacent controls carry enough separation that D-pad focus moves predictably — the TV reading of shared `A11Y-TOUCH-2`.
- `REACT-TV-UI-3` **Sizes are expressed against the platform's declared logical viewport, not a physical panel resolution measured on one device.** A TV's graphics resolution is selected per model and commonly declared in the manifest (`REACT-TV-PKG-3`), and is independent of both the panel and the video pipeline — so a size derived by measuring one device does not transfer. Follow the repository's existing scaling convention. Where the platform supports more than one graphics resolution, the layout works at each one the product ships.
- `REACT-TV-UI-4` **Text is legible at the platform's default text size**, so legibility never depends on the user having enlarged it. Shared `A11Y-FONT-1`'s obligation to respect an OS text-scale setting is unchanged wherever the target runtime exposes one to web content — a platform fact to establish, not to assume in either direction. `A11Y-FONT-2` and `A11Y-FONT-3` apply unconditionally: containers grow with content; long or translated strings must not clip, truncate meaning, or overlap.
- `REACT-TV-UI-5` **Contrast and colour account for TV display characteristics.** Text and focus indicators meet the repository's contrast requirement against their **actual** background, including over background video or imagery, where the contrast is guaranteed by the composition rather than assumed from the asset. Very large fully saturated fills and pure-white-on-pure-black are avoided where the repository's TV convention says so. **Information is never conveyed by colour alone** — this rule owns that requirement for TV surfaces; the shared accessibility standard has no colour rule to cite.
- `REACT-TV-UI-6` **A rendered-window strategy must not unmount the focused row.** `REACT-PERF-LIST-1` applies unchanged, including its lighter non-unmounting alternative for long static content. The TV-specific hazard is that an unmounted row cannot hold focus: where the chosen strategy unmounts rows, the window and the focus model are reconciled — focus approaching the window edge triggers the next page, and the focused item is never the one unmounted (`REACT-TV-FOCUS-1`).
- `REACT-TV-UI-7` **Assistive-technology support is verified with the TV platform's own screen reader.** The major TV platforms ship one, and support for it may require a manifest opt-in that defaults off (`REACT-TV-PKG-3`) — an app that omits the opt-in has no audio guidance at all, and not all models support the feature. The semantic obligation is unconditional and reachable at Diff: roles, labels, and states correct and complete (shared `A11Y-ROLES-1`, `A11Y-ROLES-2`, `A11Y-ROLES-3`), and assistive-technology traversal following reading order (shared `A11Y-SR-2`) — which is a **separate order from D-pad spatial adjacency** (`REACT-TV-FOCUS-5`), so satisfying one is never a violation of the other. The device walkthrough itself is a QA-stage obligation: shared `A11Y-SR-1` names VoiceOver and TalkBack, neither of which exists here, so the walkthrough is performed with the platform's own feature and **what it actually announced is recorded** in the QA handoff (shared `QA-A11Y-1`). Only where the target platform genuinely offers no assistive technology is a gap recorded — never a silent pass.

## Media Playback

**[Applies where the feature touches playback; otherwise N/A. Covers React-side integration — ownership, state, lifecycle, cleanup. Specifies no player, streaming protocol, DRM system, or codec; those are repository and vendor findings, and on some platforms adaptive streaming and DRM require a vendor player API rather than an HTML5 element.]**

- `REACT-TV-MEDIA-1` **The player instance is owned by one module outside the render path** — a service, a store-backed controller, or the repo's existing wrapper — not constructed in a component body or duplicated per screen. A second instance created because a route re-mounted is a defect (`REACT-ARCH-LAYERS-4`, `REACT-ARCH-LOGIC-1`).
- `REACT-TV-MEDIA-2` **Playback state has exactly one writer, derived from the player's events through a single subscription.** Two independent copies of "is playing" is a defect. Playback is externally-owned state and is not duplicated into the global store for convenience — the placement test in `REACT-STATE-BOUNDARY-3`.
- `REACT-TV-MEDIA-3` **The player is torn down on unmount and on source change** — listeners removed, buffers released, the underlying element or vendor object destroyed (`REACT-FC-5`). On a memory-capped runtime an undisposed player is a termination, not a slow leak (`REACT-TV-PERF-2`).
- `REACT-TV-MEDIA-4` **Playback survives the app lifecycle deliberately.** Suspend, background, and screensaver transitions either pause and resume at the recorded position or continue by explicit decision — never left to whatever the runtime does. The position is captured before suspension (`REACT-TV-LIFECYCLE-2`).
- `REACT-TV-MEDIA-5` **Playback errors go through the normalized error path**, not swallowed or surfaced as a raw vendor code. Normalized like any other error (`REACT-API-ERR-1`, `REACT-API-ERR-2`), distinguishing a recoverable stall from a fatal source/DRM failure (`REACT-API-ERR-3`), and leaving focus on a reachable control so the user can retry or exit (`REACT-TV-FOCUS-1`).
- `REACT-TV-MEDIA-6` **Player and media-key handling do not fight the focus model.** Transport controls are focusable within the focus model (`REACT-TV-FOCUS-2`), media keys resolve through the central key map (`REACT-TV-INPUT-1`, `REACT-TV-INPUT-5`), and an auto-hiding control overlay never hides the focused element out from under the user (`REACT-TV-FOCUS-1`).
- `REACT-TV-MEDIA-7` **The platform screensaver is suppressed during playback and restored when playback stops.** A TV suppresses its screensaver only on user input, so uninterrupted video triggers it; where the platform exposes a screensaver control, the app disables it while playing a slideshow or video and re-enables it on pause, stop, or exit. The re-enable is a cleanup obligation under `REACT-FC-5` — a screensaver left disabled after the player unmounts is a defect, and burn-in protection is not the app's to switch off permanently.

## App Lifecycle

**[The events and APIs are platform-specific. Identify the repository's actual lifecycle integration; where the platform is not established, mark `[unknown]` rather than assuming one vendor's model.]**

- `REACT-TV-LIFECYCLE-1` **Lifecycle integration goes through one module.** Suspend/resume/relaunch/exit and locale-change handling is owned by a single app-level module the rest of the app subscribes to — not a `visibilitychange` or vendor-event listener added independently in several components. Every listener carries a cleanup (`REACT-FC-5`).
- `REACT-TV-LIFECYCLE-2` **State that must survive suspension is captured before suspension, not on resume.** Playback position, in-progress input, and scroll/focus position are recorded when the app is notified it is backgrounding; code reading them after resume has already lost them. Persistence follows `REACT-STATE-PERSIST-1` and never writes tokens or PII to a script-readable store (`REACT-STATE-PERSIST-2`, shared `SEC-COOKIE-2`, `SEC-STORAGE-3`).
- `REACT-TV-LIFECYCLE-3` **Resume and relaunch are distinguished from a cold start, and a relaunch payload is untrusted input.** A launch or relaunch parameter is validated before it drives navigation or state change (shared `SEC-WEB-5`, `SEC-DEEPLINK-2`, and `REACT-ROUTE-SECURITY-1`), and never authenticates a user on its own.
- `REACT-TV-LIFECYCLE-4` **Work stops when the app is not visible.** Timers, polling, animations, prefetching, and open subscriptions suspend on background and resume on foreground rather than consuming a constrained device off screen.
- `REACT-TV-LIFECYCLE-5` **Runtime locale change is handled rather than requiring a restart** where the platform emits it: localized strings re-resolve and layout direction is re-evaluated (shared `I18N-RTL-1`, `I18N-RTL-2`), including focus adjacency per `REACT-TV-FOCUS-8`.

## Network & Auth Transport

**[Applies where the feature performs network requests. Every `REACT-API-*` rule still applies; these exist because two browser premises may not hold on a TV target.]**

- `REACT-TV-API-1` **The auth transport is established for the target runtime and app type, never assumed from browser behavior.** `REACT-API-BASEQ-2` prefers an `httpOnly`, `Secure`, `SameSite` cookie over a script-readable token, and that is correct **wherever cookie transport works**. A TV platform distinguishes a **packaged** app (resources installed locally, served from a non-`http(s)` scheme) from a **hosted** app (served over `http(s)`), and cookie behavior may differ between them. Establish which the repository ships and whether cookies are usable, and record it with its source. Do not assume in either direction.
- `REACT-TV-API-2` **Where cookie transport is unavailable, the in-memory token path is the primary design, not a compromise.** `REACT-API-BASEQ-2`'s in-memory fallback becomes correct. Nothing relaxes: never persisted to a script-readable store (`REACT-STATE-PERSIST-2`, shared `SEC-COOKIE-2`, `SEC-STORAGE-3`), never logged (shared `SEC-LOG-1`), never baked into the package (`REACT-TV-PKG-6`, shared `SEC-SECRETS-2`). **Reaching for `localStorage` because "cookies don't work on TV" is a defect, not a workaround** — including mirroring a cookie into it to survive restarts. Where the platform offers a non-script-readable credential store, prefer it over a long-lived in-memory credential.
- `REACT-TV-API-3` **The cross-origin model is established from the platform, not assumed to be ordinary browser CORS.** A packaged app's document origin is not the API's origin, so requests are cross-origin by construction, and platforms mediate that differently: one may require every reachable origin declared in the application manifest, and a platform may not send the CORS `Origin` request header at all — which breaks any server that reflects or echoes the app origin. Establish the target's model before designing the request path, and treat a manifest origin allowlist as part of the feature (`REACT-TV-PKG-3`) — a new backend host may be a packaging change. Unchanged: CORS is a read boundary, never authorization (`REACT-API-BASEQ-5`, shared `SEC-WEB-6`), and a permissive allowlist never substitutes for access control. Vendor guidance suggesting JSONP as a cross-origin remedy is **not** acceptable under shared `SEC-WEB-1`.
- `REACT-TV-API-4` **CSRF exposure is re-derived for the actual transport, not inherited.** `REACT-API-BASEQ-3` and shared `SEC-WEB-3` require protection when state changes ride an **ambient cookie** credential. Where the established TV transport carries none, classic browser CSRF is not the live threat — recorded as a **reasoned N/A against the established transport**, never a passed check, and re-derived if the transport changes. An explicitly attached bearer token is not ambient.

## Constrained Runtime & Memory Budget

**Lane: `react-performance-reviewer`.** Inherits the **measurement discipline** in `react-performance.md` in full — a magnitude claim is a measurement request (metric, scenario, threshold), never asserted from reading code; production-build-only items are marked as such. On TV, measured **on the target device tier**: a desktop profile is not weak evidence, it is no evidence.

- `REACT-TV-PERF-1` **A TV surface has an explicit, stated memory and performance budget**, sourced from the device tier the product ships to — not inherited from the phone-web budget and not left implicit. Derive it in this order: the repository's existing TV budget convention → the vendor's published tier floor → an unresolved decision naming who supplies the tier. A manifest memory declaration is a **minimum required to launch**, not a ceiling and not the peak, so it does not substitute for a measured budget, though the two must be mutually plausible. Where no budget is stated, a measurement request records its threshold as *unset — no stated TV budget*, and the absence is filed once against the change consuming budget without one.
- `REACT-TV-PERF-2` **Memory is released, not merely dereferenced, on navigation away from a screen.** Large image and video assets, player instances (`REACT-TV-MEDIA-3`), caches, and detached DOM subtrees are disposed. A retained reference harmless on a desktop browser is a termination on a TV. Verified against the `REACT-TV-PERF-1` budget rather than asserted from reading code.
- `REACT-TV-PERF-3` **Image assets are sized to the logical viewport and decoded at display size.** `REACT-PERF-IMAGE-1` applies, with the TV constraint that a full-resolution asset decoded for a small tile consumes decoded-bitmap budget, not just download bytes, and that off-screen assets in a long rail are not all held decoded (`REACT-TV-UI-6`). Which image formats the runtime decodes is a platform fact (`REACT-TV-PERF-7`), not assumed from the desktop.
- `REACT-TV-PERF-4` **Animation work is bounded by the stated budget.** The number of concurrent animations is bounded by a value in the repository's TV budget (`REACT-TV-PERF-1`), and an effect that cannot hold frame rate on the target tier is dropped for TV rather than shipped degraded. Frame-rate claims are measured on the target device.
- `REACT-TV-PERF-5` **Long tasks are more severe than on desktop.** `REACT-PERF-MAINTHREAD-1` applies with lower tolerance: on a slower single-threaded engine, minor desktop jank becomes an unresponsive remote. Responsiveness to a key press is the user-facing signal, in place of a pointer-derived INP measurement.
- `REACT-TV-PERF-6` **The bundle is budgeted for parse and execute cost, not only download size.** `REACT-PERF-BUNDLE-1..3` apply, with the TV addition that script parse/compile on an older engine is itself a startup cost — a locally packaged app with no download still pays it. Startup-path splitting is judged against time-to-interactive on the target tier, on a production build.
- `REACT-TV-PERF-7` **Engine capability is established from the shipped firmware, not from the build configuration.** A TV runtime's engine is fixed by firmware and typically years behind the development browser. The transpilation target and polyfill set must match the engine the shipped firmware actually runs, established from the vendor's documentation for that firmware; **a build configuration targeting a newer engine than the shipped runtime is itself the defect**, not the authority. A modern API used without confirming support is a defect — and its *absence* is never raised as a modernization aside.

## Vendor Packaging, Manifest & Signing

**[Governs how the repository handles packaging config. Reachable only when packaging config is in the reviewed scope — see *Stages*. Does not restate vendor manifest schemas; the vendor's current documentation is authoritative.]**

- `REACT-TV-PKG-1` **The packaging target and toolchain are declared in the repository**, as committed scripts invoking the vendor CLI, so a release is reproducible by someone who did not author it. **A working packaging toolchain is never a finding on the grounds that the vendor has superseded it** — the no-aside stance applies here as it does to engine APIs.
- `REACT-TV-PKG-2` **The vendor manifest is source: reviewed like code and diffed against the last release.** A change to app id, version, entry point, privileges, declared capabilities, or resolution is attributable to a reviewed change. This is the TV instance of shared `REL-NATIVECONFIG-1`, and an unexplained manifest diff is a blocker (shared `REL-NATIVECONFIG-2`).
- `REACT-TV-PKG-3` **Required manifest metadata is present, valid, and consistent with actual behavior** — the fields the target platform requires for store acceptance, plus the ones other rules depend on: the graphics **resolution** (`REACT-TV-UI-3`), any memory declaration (`REACT-TV-PERF-1`), any assistive-technology opt-in (`REACT-TV-UI-7`), and any reachable-origin allowlist (`REACT-TV-API-3`). A privilege declared but unused is removed; a capability used but undeclared is a defect. The vendor's current documentation defines the required set.
- `REACT-TV-PKG-4` **The manifest version is bumped with the package version every release, and matches it** — a lagging manifest version ships the wrong build (shared `REL-VERSION-1`, `REL-VERSION-2`).
- `REACT-TV-PKG-5` **Signing material never lives in the repository.** Certificates, private keys, keystores, store credentials, and vendor account tokens are held outside source control and injected at build time, and certificate paths and passwords are not hardcoded into a committed script (shared `SEC-SECRETS-1`, `SEC-SECRETS-3`, `SEC-SECRETS-4`). TV-specific: the **author certificate must survive for future updates** — a package signed with a different author certificate is treated as a different application, not an update — so it is preserved and backed up outside the repository rather than regenerated.
- `REACT-TV-PKG-6` **Nothing secret is baked into the packaged app.** A TV package is a locally installed, unpacked bundle — everything inside is readable, so a build-time constant in it is public (shared `SEC-SECRETS-2`, `REACT-API-BASEQ-6`). A call needing a secret goes through a server, never the TV client. Release hardening follows shared `SEC-HARDEN-2` and `SEC-HARDEN-3`.
- `REACT-TV-PKG-7` **Environment configuration is resolved per target, and the shipped package's target is verified before submission.** A package built against staging and submitted to a store is release-blocking; env vars are set deliberately per target (shared `REL-ENV-1`) with no real secret among them (shared `REL-ENV-2`).
- `REACT-TV-PKG-8` **Store and distribution metadata changes are recorded for the release** — listing assets, description, release notes, declared capabilities per vendor store — the TV reading of shared `REL-STORE-1`. Vendor certification requirements are release criteria, and an unverifiable item defaults to No-Go (shared `REL-VERDICT-1`). See the *Release-stage note*: no release-stage agent checks this today.
