# React Smart TV Standards

## Purpose & Scope

These standards apply to React (web) application code running on a **Smart TV** surface — a Samsung Tizen or LG webOS TV web application, a vendor browser-based TV runtime, or a browser build driven by a remote control — reviewed by `react-code-reviewer` and `react-performance-reviewer` via `/review-code`, planned by `react-architect` via `/analyze-feature` and `/dev-design-start`, and implemented by `react-feature-developer` via `/implement-task`. Each rule carries a stable `REACT-TV-*` ID so findings and design proposals cite the exact rule they apply. This is a baseline, not exhaustive.

**Smart TV is `device_type: tv` inside the React platform — never a platform of its own.** The `platform` enum is `react-native` / `ios` / `android` / `react`; the `device_type` enum is `mobile` / `tv`. There is no `react-tv` platform value, no `mixed` device type, and no TV-specific agent, skill, or command. The same four React agents and three React skills serve both device types, selecting this document by `device_type`.

This document inherits the **React lane conventions** in `standards/react/react-coding-standards.md` — the repository-first source-of-truth hierarchy (a repo's established TV model outranks these rules; official vendor docs are rank-5 supporting only; absence of a convention is not compliance), technology-neutrality, the no-modernization-aside stance, the `REACT-` ID prefix, and the `## External references` pattern. Findings are limited to code introduced or modified in the reviewed scope.

**Every rule in the six base React standards still applies on a TV surface.** This document adds TV-specific obligations; it does not replace, relax, or fork the base rules. A component on a TV surface is still bound by `REACT-FC-*`, `REACT-ARCH-*`, `REACT-ROUTE-*`, `REACT-STATE-*`, `REACT-API-*`, and `REACT-PERF-*`. Where a base rule assumes a pointer, this document names the TV equivalent rather than waiving the base rule.

> **Additive by construction.** This document was authored after the REACT-001 ID freeze (2026-08-16). It defines a new `REACT-TV-*` root and **renumbers nothing**. No existing `REACT-TS/FC/NAME/PROPS/LINT/ARCH/API/ROUTE/STATE/PERF` ID changes meaning or number because this file exists.

## Lane ownership (governing — this root has no default owner)

The React lane separates correctness, performance, and security by **the cited ID's own root**, so the two reviewers cannot double-file. A standalone `REACT-TV-*` root does not resolve under that mechanical rule on its own, so its routing is stated here explicitly and is the only correct routing:

| Family | Filed by | Stage |
|---|---|---|
| `REACT-TV-FOCUS-*` | `react-code-reviewer` | Diff |
| `REACT-TV-INPUT-*` | `react-code-reviewer` | Diff |
| `REACT-TV-UI-*` | `react-code-reviewer` | Diff |
| `REACT-TV-MEDIA-*` | `react-code-reviewer` | Diff |
| `REACT-TV-LIFECYCLE-*` | `react-code-reviewer` | Diff |
| `REACT-TV-PERF-*` | `react-performance-reviewer` | Diff + Release |
| `REACT-TV-PKG-1..4`, `REACT-TV-PKG-7..8` | `react-code-reviewer` (packaging-config diff) · release sign-off via shared `REL-*` | Build / Release |
| `REACT-TV-PKG-5`, `REACT-TV-PKG-6` | **shared `mobile-security-reviewer`**, via the `SEC-*` IDs they cite | Build / Release |

Rules:

- **`REACT-TV-PERF-*` is the performance reviewer's, and nothing else here is.** The performance reviewer files `REACT-PERF-*` and `REACT-TV-PERF-*` only. Every other `REACT-TV-*` family belongs to `react-code-reviewer`, even when the concern *sounds* performance-adjacent (a focus-restoration bug that feels sluggish is still `REACT-TV-FOCUS-*`, filed by the code reviewer).
- **Security stays with the shared `mobile-security-reviewer`, including the two packaging rules that are really security rules.** No rule below re-authors a `SEC-*` rule. `REACT-TV-PKG-5` (signing material in the repository) and `REACT-TV-PKG-6` (secrets inside the package) exist to say *where on a TV target* the shared secrets rules bite; the defect is filed as the `SEC-*` ID by the security reviewer, and the `REACT-TV-PKG-*` number is cited as the TV-specific pointer, never filed by the React lane instead. The other six `REACT-TV-PKG-*` rules are ordinary configuration/release-process rules and are the React lane's.
- **Applicability stage.** A `REACT-TV-PKG-*` rule is generally unreachable from a diff of application code. When the reviewed scope cannot reach a rule, record it **Not Applicable** with the reason — never as passed, and never as a finding. This mirrors the measurement and applicability discipline in `react-performance.md`.
- **`/prepare-mobile-release` is the real enforcement point for `REACT-TV-PKG-*`**, not `/review-code`. Because a packaging rule is normally unreachable from an application-code diff, a family recorded Not Applicable at every review would otherwise never be checked anywhere. The release stage is where the manifest diff, version bump, environment target, signing material, and store metadata are actually verified — via shared `REL-NATIVECONFIG-1/2`, `REL-VERSION-1/2`, `REL-ENV-1/2`, `REL-STORE-1`, and `REL-VERDICT-1`. A review that marks the family N/A is correct; a release that does is not.

### One defect, one finding

**File what your lane sees; never suppress an observation assuming the other reviewer will file it.** The two reviewers cannot read each other's output, so silence is not coordination. Where one real defect satisfies more than one rule, the table below names the **owning ID** — the finding is filed once under that ID, with the others cited inside it as supporting context. The `react-code-review` skill dedupes at merge using this table.

| Defect | Owning ID | Supporting IDs, cited inside |
|---|---|---|
| Player left undisposed on unmount or source change | `REACT-TV-MEDIA-3` | `REACT-TV-PERF-2`, `REACT-FC-5` |
| Memory retained on navigating away from a screen | `REACT-TV-PERF-2` | `REACT-TV-PERF-3`, `REACT-TV-MEDIA-3` |
| Full-resolution asset decoded for a small display context | `REACT-TV-PERF-3` | `REACT-PERF-IMAGE-1` |
| Virtualized row unmounted while it holds focus | `REACT-TV-UI-6` | `REACT-PERF-LIST-1`, `REACT-TV-FOCUS-1` |
| Key/lifecycle listener added without a cleanup | `REACT-FC-5` | `REACT-TV-INPUT-3`, `REACT-TV-LIFECYCLE-1` |
| Focus lost or reset after a transition | `REACT-TV-FOCUS-1` | `REACT-TV-FOCUS-4` |
| Numeric key code hardcoded in a component | `REACT-TV-INPUT-1` | `REACT-TV-INPUT-2` |
| Signing material or a secret committed to the repository | shared `SEC-SECRETS-1` (security reviewer) | `REACT-TV-PKG-5`, `REACT-TV-PKG-6`, `SEC-SECRETS-3/4` |

A collision whose owning ID belongs to the **other** lane is still worth recording: cite it as context in your own finding rather than filing the other lane's ID, and let the merge step reconcile.

## Applicability: is this a TV surface at all?

This document applies **only** to a surface that actually runs on a TV. Establish that from evidence before citing any rule below; on a repository with no TV surface, this entire document is **N/A** and none of its rules may be raised.

- At **planning and implementation** time, `device_type` is read from the task/DD frontmatter and is authoritative — never re-detected, never defaulted to `mobile`.
- At **review** time there is no confirmed `device_type`. Infer the surface from the reviewed files, note the inference in Scope, and do not block to ask. A file that is plainly part of a shared, device-agnostic layer is not made a TV file by living in a repo that also ships a TV app.

**Evidence that establishes a TV surface** (any of, labelled per the lane's `[evidence:path]` convention): a vendor manifest (`config.xml` with a Tizen namespace, `appinfo.json`); a vendor packaging or CLI script in `package.json`; a vendor platform API reference in source (`window.tizen`, `window.webOS`, `webOSDev`); a spatial-navigation or TV-focus dependency; a TV-only route/entry point or build target; a TV component folder or screen wrapper.

### TV detection traps

Each trap names the confident-but-wrong finding it prevents. Prefer the authoritative signal; mark `[unknown]` rather than guess.

- **A TV dependency in `package.json` ≠ a TV surface for this diff.** A monorepo or multi-target repo may ship both a mobile web app and a TV app from shared code. The **surface the changed file renders on** decides applicability, not the repo's dependency list. *Prevents:* filing `REACT-TV-FOCUS-*` against a shared design-system component whose only consumer in this diff is the phone web app.
- **A shared component is not automatically TV-compliant or TV-exempt.** A component used by both surfaces must satisfy both; a TV obligation on it is real, but a *pointer-only* affordance in it is a defect only if the TV surface actually renders it. *Prevents:* both the false pass and the false finding on shared code.
- **`window.tizen` / `window.webOS` guarded at runtime ≠ the vendor runtime is the target.** Feature-detection guards are also written for graceful degradation in a desktop browser used for development. Confirm the build target from the packaging script or manifest. *Prevents:* "this is a Tizen app" from one guarded reference.
- **A TV app may run in a plain browser during development.** Pointer events working in the dev browser proves nothing about the shipped remote-driven surface. *Prevents:* accepting a hover-only affordance because it was verified in Chrome.
- **`@media (pointer: coarse)` / `hover: none` do not identify a TV.** Those queries describe touch, and a TV is neither touch nor hover-capable in the way the queries model; vendor runtimes vary in what they report. Do not treat a media query as the device-type signal. *Prevents:* a layout or affordance decision keyed to the wrong device class.
- **Tizen and webOS are different platforms with different manifests, key codes, packaging, and lifecycle events.** Neither is a stand-in for the other, and a repo may target both. *Prevents:* citing a webOS manifest requirement against a Tizen-only app, or assuming one key-code table covers both.
- **Screen resolution does not imply the device.** A 1920×1080 viewport is as likely a desktop browser as a TV, and TV runtimes commonly render a 1920×1080 logical viewport on a 4K panel. *Prevents:* inferring the device tier, or a physical pixel budget, from the viewport size.

## Focus & Spatial Navigation

The remote is the only pointer. Focus is not a decoration on a TV surface — it **is** the cursor, and losing it strands the user with no way to recover except restarting the app.

- `REACT-TV-FOCUS-1` **Exactly one element holds focus at all times, and it is never lost.** Every screen, route, modal, and async state has a defined focus target; after any transition, list refresh, or conditional re-render, focus lands on a deliberate element. Focus is never left on a removed or hidden node, and never dropped to `document.body` — with no pointer, a user cannot recover it.
- `REACT-TV-FOCUS-2` **Focus movement follows the repository's existing focus model**, whichever it is: a spatial-navigation library, a custom focus engine, the platform's built-in navigation, or explicit key handling. The model is identified from the repository before any focus code is written; a second, parallel focus mechanism is never introduced alongside an existing one, and a bespoke engine is never hand-rolled where the repo already has one.
- `REACT-TV-FOCUS-3` **The focused element carries a clearly visible focus indicator** that is unambiguous from across a room — sufficient contrast and size to read at a 10-foot viewing distance, not a 1px outline or a subtle tint. The browser default outline is never suppressed (`outline: none`) without an equally visible replacement. This is how shared `A11Y-TOUCH-1` is satisfied on a TV form factor, where there is no touch target to measure; it is also the TV reading of `A11Y-ROLES-3`, since focus is the state the user navigates by.
- `REACT-TV-FOCUS-4` **Focus is restored on return, not reset.** Navigating back to a previously visited screen, or returning from a modal, overlay, or player, restores focus to the element the user left — the previously focused row and item in a grid, not the first cell. Where restoration state must survive a route change, it is placed per the state-placement rules (`REACT-STATE-BOUNDARY-*`; URL-appropriate state per `REACT-STATE-BOUNDARY-2`).
- `REACT-TV-FOCUS-5` **Focus order matches the visible spatial layout.** Moving Up/Down/Left/Right moves to the element that is actually adjacent on screen, not to the next node in DOM order. Where DOM order and visual order diverge (a CSS grid, an absolutely positioned rail, a reordered flex container), the adjacency is stated explicitly rather than left to DOM order. This is the spatial counterpart of shared `A11Y-SR-2`.
- `REACT-TV-FOCUS-6` **Overlays, modals, and dialogs trap focus** for as long as they are open — focus cannot escape to the content behind them — and release it back to the invoking element on close. An open overlay that lets D-pad focus wander into the obscured page beneath it is a defect (shared `A11Y-SR-2`).
- `REACT-TV-FOCUS-7` **A focusable element is reachable and a non-interactive element is not focusable.** Every interactive control can be reached by some sequence of remote presses — no control is stranded behind an unreachable adjacency — and decorative or static content is not inserted into the focus order (shared `A11Y-ROLES-4`). An element made focusable purely to receive key events, without being an interactive control, is a defect.
- `REACT-TV-FOCUS-8` **Under RTL, focus movement stays spatial and the mirroring is deliberate.** `REACT-TV-FOCUS-5` governs: a D-pad press moves to the element **visually adjacent in that direction**, and that does not change under RTL. So when a layout mirrors for an RTL locale (shared `I18N-RTL-1`, `I18N-RTL-2`), pressing Right moves to the element now drawn to the right — which in a mirrored rail is the *earlier* item in reading order. That is correct: the remote maps to screen geometry, not to reading order. What this rule requires is that the mirroring be **intentional and verified** rather than incidental: the layout mirrors, focus adjacency mirrors *with* it, and no rail ends up navigating against its own visuals — the failure mode is a container whose CSS mirrors while its focus adjacency stays hardcoded LTR (or vice versa), which strands the user. Directional-input behavior is checked as part of the bidirectional walkthrough required by shared `I18N-TEST-2`, alongside `I18N-TEST-1`. Where a repository has deliberately chosen reading-order semantics for a specific control, that is a repository convention (rank 2) and is followed — but it is stated, not assumed.

## Remote & Key Input

- `REACT-TV-INPUT-1` **Key codes are defined once in a central, named mapping** — never as numeric literals scattered through component code. `if (e.keyCode === 10009)` in a component is a defect; a named constant resolved through one platform-aware key map is the requirement. The mapping's values come from the target platform's official key-code reference (see *External references*), not from values observed empirically on one device.
- `REACT-TV-INPUT-2` **The key map is per-platform and selected at runtime, not merged into one table.** Tizen and webOS assign different codes to the same logical key — Back most notably — so a single hardcoded table silently breaks on the other platform. Where the repo targets both, the logical key (`BACK`, `OK`, `PLAY_PAUSE`) is what application code names; the platform mapping resolves it.
- `REACT-TV-INPUT-3` **Key handling is scoped to the focused subtree, not attached globally per component.** A component that registers a `keydown` listener on `window` or `document` for its own keys competes with every other mounted component. Key handling belongs to the focus model (`REACT-TV-FOCUS-2`); where a global listener is genuinely required (an app-level Back handler), there is one, owned by a single module. Every listener obeys `REACT-FC-5` — a listener added in an effect without a cleanup leaks and double-binds.
- `REACT-TV-INPUT-4` **The Back key is handled deliberately at every level and always has an effect.** Back closes the topmost overlay, or navigates up one level, or — at the app's root — exits or prompts to exit per the platform's convention; it is never a no-op that traps the user, and never silently swallowed by a component that forgot to handle it. Back-driven navigation goes through the router rather than raw `history` manipulation (`REACT-ROUTE-SERVICE-3`), and `REACT-ROUTE-UX-3`'s prohibition on corrupting history applies unchanged.
- `REACT-TV-INPUT-5` **Media and color keys are registered before use where the platform requires registration.** On a platform whose runtime only delivers certain hardware keys after the app registers interest in them, that registration is performed explicitly and is part of the feature, not assumed. A handler for a key the app never registered is dead code that will read as working on a keyboard and fail on a remote.
- `REACT-TV-INPUT-6` **No pointer, hover, or gesture affordance is load-bearing.** Hover-reveal, tap, swipe, drag, long-press, and pointer-scroll do not exist on a remote-driven surface. Any information or action reachable only through one of them is unreachable on TV; the D-pad path is the primary path, and a pointer path — where the platform offers a pointer mode — is additive only. Horizontal rails and carousels scroll by focus movement, not by a drag or a scrollbar.

## 10-Foot UI & Layout

- `REACT-TV-UI-1` **Layout is overscan-safe.** Interactive controls and essential text stay inside a safe area inset from every screen edge, so nothing critical is clipped on a panel that overscans. The inset follows the platform's published safe-area guidance and the repository's existing TV layout convention — it is a stated value in one place, not an ad-hoc margin re-guessed per screen. Full-bleed background imagery may extend to the edge; content may not.
- `REACT-TV-UI-2` **Type, controls, and spacing are sized for a 10-foot viewing distance**, following the repository's TV scale. Phone or desktop type ramps and touch-target sizes are not reused on a TV surface — they are legible at arm's length, not across a room.
- `REACT-TV-UI-3` **The layout targets the platform's logical viewport and scales, rather than pinning pixel sizes to one panel resolution.** A TV runtime commonly presents a fixed logical viewport regardless of the physical panel, so sizes are expressed in the repo's scaling convention (relative units or its scale helper), never as absolute pixels measured on one device. Do not infer the device tier or a pixel budget from the viewport size (see *TV detection traps*).
- `REACT-TV-UI-4` **Text is legible at the platform's default text size, without depending on a user text-scale setting to become so.** Shared `A11Y-FONT-1` requires respecting the OS font-scale / Dynamic Type setting; that obligation is unchanged **wherever the target runtime exposes such a setting to web content — which is a per-platform, per-firmware fact to establish from the vendor's current documentation, not to assume in either direction** (this document deliberately makes no claim about which runtimes do). What this rule adds is that TV base type sizes must already be readable at a 10-foot distance at the default, so legibility never *depends* on the user having enlarged it. `A11Y-FONT-2` and `A11Y-FONT-3` apply in full and unconditionally: containers grow with their content, and long or translated strings must not clip, truncate meaning, or overlap.
- `REACT-TV-UI-5` **Contrast and color account for TV display characteristics.** Text and focus indicators meet the repository's contrast requirement against their actual background — including over background video or imagery, where a scrim or plate is used rather than relying on the asset — and pure-white-on-pure-black or fully saturated large fills are avoided where the repo's TV convention says so. Information is never conveyed by color alone (shared `A11Y-ROLES-3`).
- `REACT-TV-UI-6` **Long rails and grids are virtualized, and their focus model survives virtualization.** `REACT-PERF-LIST-1` applies with a TV-specific hazard: a row that is unmounted by virtualization cannot hold focus, so the focus model and the virtualization window are reconciled — focus moving toward the edge of the rendered window triggers the next page, and the focused item is never the one that gets unmounted (`REACT-TV-FOCUS-1`). Stable keys are required, per `REACT-PERF-LIST-1`.
- `REACT-TV-UI-7` **Screen-reader support is verified with the TV platform's own assistive technology, not assumed from mobile.** Shared `A11Y-SR-1` names VoiceOver and TalkBack, neither of which exists on a TV runtime — but the major TV platforms do ship their own screen reader (Samsung's Voice Guide, and LG's equivalent), so **the default is to perform the walkthrough with the platform's feature and record what it actually announced**, not to declare the check unavailable. How completely a TV screen reader traverses *web application* content varies by platform and firmware and is itself worth recording. The semantic obligation is unconditional either way: roles, labels, and states are correct and complete (shared `A11Y-ROLES-1`, `A11Y-ROLES-2`, `A11Y-ROLES-3`) and focus order follows visual order (`A11Y-SR-2`, and `REACT-TV-FOCUS-5`). Only where the target platform genuinely offers no assistive technology is the check recorded as a stated gap in the QA handoff (shared `QA-A11Y-1`) — never as a silent pass, and never as a shortcut around trying.

## Media Playback

**[Applies where the feature touches video/audio playback. On a TV surface with no playback, this section is N/A — do not raise its rules as findings.]**

Playback **is** in scope for React Smart TV: a TV application is overwhelmingly a media application, and the player is where the platform's constraints, lifecycle, and memory pressure concentrate. This section covers the **React-side integration** with a player — ownership, state, lifecycle, and cleanup. It does not specify a player, a streaming protocol, a DRM system, or codec support; those are repository and vendor findings.

- `REACT-TV-MEDIA-1` **The player instance is owned by one module outside the component tree's render path** — a service, a store-backed controller, or the repo's existing player wrapper — not constructed inside a component body or duplicated per screen. A second player instance created because a route re-mounted is a defect. This follows `REACT-ARCH-LAYERS-4` and `REACT-ARCH-LOGIC-1`.
- `REACT-TV-MEDIA-2` **Playback state is read from the player as the source of truth, not mirrored into a store that can diverge.** Where playback state must be shared, it is derived from the player's events through a single subscription; two independent copies of "is playing" is a defect. The player is externally-owned state, so it is not copied into the global store for convenience — the same placement test as `REACT-STATE-BOUNDARY-3`.
- `REACT-TV-MEDIA-3` **The player is torn down on unmount and on source change** — listeners removed, buffers released, the underlying element or vendor object destroyed — per `REACT-FC-5`. On a memory-constrained TV runtime an undisposed player is not a slow leak but a crash (`REACT-TV-PERF-2`).
- `REACT-TV-MEDIA-4` **Playback survives the app lifecycle deliberately.** Suspend, background, and screen-saver transitions either pause and resume at the recorded position or continue by explicit decision — never left to whatever the runtime happens to do. The position is captured before suspension so resume does not restart the asset (`REACT-TV-LIFECYCLE-2`).
- `REACT-TV-MEDIA-5` **Playback errors are surfaced through the normalized error path**, not swallowed or shown as a raw vendor error code. A player error is normalized like any other (`REACT-API-ERR-1`, `REACT-API-ERR-2`), distinguishes a recoverable network stall from a fatal source/DRM failure (`REACT-API-ERR-3`), and leaves focus on a reachable control so the user can retry or exit (`REACT-TV-FOCUS-1`).
- `REACT-TV-MEDIA-6` **Player and media-key handling do not fight the focus model.** Transport controls are focusable elements in the focus model (`REACT-TV-FOCUS-2`), media keys resolve through the central key map (`REACT-TV-INPUT-1`, `REACT-TV-INPUT-5`), and a control overlay that auto-hides never hides the focused element out from under the user (`REACT-TV-FOCUS-1`).

## App Lifecycle

**[The events and APIs named here are platform-specific. Identify the repository's actual lifecycle integration before citing a rule; where the platform is not established, mark `[unknown]` rather than assuming one vendor's model.]**

- `REACT-TV-LIFECYCLE-1` **Lifecycle integration goes through one module, not scattered listeners.** Suspend/resume/relaunch/exit and locale-change handling is owned by a single app-level module that the rest of the app subscribes to — not a `visibilitychange` or vendor-event listener added independently in several components. Every listener carries a cleanup (`REACT-FC-5`).
- `REACT-TV-LIFECYCLE-2` **State that must survive suspension is captured before suspension, not on resume.** Playback position, in-progress form input, and scroll/focus position are recorded when the app is notified it is being backgrounded; code that tries to read them after resume has already lost them. Persistence follows `REACT-STATE-PERSIST-1`, and never writes tokens or PII to a script-readable store (`REACT-STATE-PERSIST-2`, shared `SEC-COOKIE-2`, `SEC-STORAGE-3`).
- `REACT-TV-LIFECYCLE-3` **Resume and relaunch are distinguished from a cold start, and a relaunch payload is treated as untrusted input.** A relaunch that carries a deep-link or launch parameter is validated before it is used to navigate or change state — the same obligation as shared `SEC-WEB-5` and `REACT-ROUTE-SECURITY-1` for a redirect target, and `SEC-DEEPLINK-2` for a launch payload. A launch parameter never authenticates a user or performs a state change on its own.
- `REACT-TV-LIFECYCLE-4` **Work stops when the app is not visible.** Timers, polling, animations, prefetching, and open network subscriptions are suspended on background and resumed on foreground, rather than continuing to consume a constrained device's CPU and memory while off screen (`REACT-TV-PERF-1`).
- `REACT-TV-LIFECYCLE-5` **Locale change at runtime is handled rather than requiring a restart** where the platform emits it: the app re-resolves localized strings and re-evaluates layout direction (shared `I18N-RTL-1`, `I18N-RTL-2`), including focus-direction mirroring per `REACT-TV-FOCUS-8`.

## Constrained Runtime & Memory Budget

**Lane: `react-performance-reviewer`.** These rules inherit the **measurement discipline** in `react-performance.md` in full — a magnitude or regression claim is written as a measurement request (metric, scenario, threshold), never asserted from reading code, and production-build-only items are marked as such.

The premise of this family: **a TV is not a phone, and a phone is not a desktop.** A TV runtime typically offers a fraction of a contemporary phone's CPU and a hard, comparatively small memory ceiling per application, with an older browser engine and no thermal or memory headroom to absorb waste. Exceeding the ceiling does not degrade gracefully — the runtime terminates the app.

- `REACT-TV-PERF-1` **A TV surface has an explicit, stated memory and performance budget**, sourced from the target device tier the product actually ships to and the repository's existing TV budget convention — not inherited from the phone-web budget and not left implicit. Where the platform's manifest declares a memory requirement (`REACT-TV-PKG-3`), the declared value and the budget agree.
- `REACT-TV-PERF-2` **Memory is released, not merely dereferenced, on navigation away from a screen.** Large image and video assets, player instances (`REACT-TV-MEDIA-3`), caches, and detached DOM subtrees are disposed when a screen is left. A retained reference that is harmless on a desktop browser is a termination on a TV. Compliance is verified against the budget in `REACT-TV-PERF-1` rather than asserted from reading code.
- `REACT-TV-PERF-3` **Image assets are sized to the logical viewport and decoded at display size.** `REACT-PERF-IMAGE-1` applies with the TV-specific constraint that a full-resolution asset decoded for a small rail tile consumes budget in decoded bitmap memory, not just download bytes. Off-screen assets in a long rail are not all held decoded at once (`REACT-TV-UI-6`).
- `REACT-TV-PERF-4` **Animation and transition work is bounded to what the device tier can sustain.** Animations stay on compositor-friendly properties, concurrent animations are limited, and a decorative effect that cannot hold frame rate on the target tier is dropped for TV rather than shipped degraded. Frame-rate claims follow the measurement discipline — measured on the target device, never inferred from a desktop profile.
- `REACT-TV-PERF-5` **Long tasks are treated as more severe than on desktop.** `REACT-PERF-MAINTHREAD-1` applies with a lower tolerance: on a slower single-threaded engine, work that is a minor jank on desktop becomes an unresponsive remote. Input responsiveness to a key press is the user-facing signal, in place of a pointer-derived INP measurement.
- `REACT-TV-PERF-6` **The bundle is budgeted for a slow engine's parse and execute cost, not only for download size.** `REACT-PERF-BUNDLE-1`, `REACT-PERF-BUNDLE-2`, and `REACT-PERF-BUNDLE-3` apply, with the TV addition that script parse/compile time on an older engine is itself a startup cost — a locally packaged app with no network download still pays it. Startup-path code-splitting is judged against time-to-interactive on the target device tier, measured on a production build.
- `REACT-TV-PERF-7` **Browser-engine capability is established from the target runtime, not assumed current.** A TV runtime's engine is typically several years behind the desktop browser used for development, and its version is fixed by the firmware, not updatable by the user. The required transpilation target and polyfill set follow the repository's build configuration for that target. A modern API used without confirming support on the shipped runtime is a defect, not a modernization improvement — and its *absence* is never raised as a modernization aside (see the no-aside stance in `react-coding-standards.md`).

## Vendor Packaging, Manifest & Signing

**[Applies to the packaging and manifest configuration of a TV application. Generally unreachable from a diff of application code — record Not Applicable with the reason where the reviewed scope cannot reach it, per *Lane ownership*.]**

Packaging is vendor-specific and version-sensitive. These rules govern **how the repository handles packaging config**, and deliberately do not restate the vendors' field-by-field manifest schemas — those are rank-5 external references, and the vendor's current documentation is authoritative over any list frozen into this file.

- `REACT-TV-PKG-1` **The packaging target and toolchain are declared in the repository, not reconstructed by hand at release time.** The build/package/install steps for each TV target are committed scripts (a `package.json` script or a checked-in build script invoking the vendor CLI), so a release is reproducible by someone who did not author it.
- `REACT-TV-PKG-2` **The vendor manifest is treated as source, reviewed like code, and diffed against the last release.** A change to a Tizen `config.xml` or a webOS `appinfo.json` — app id, version, entry point, privileges/permissions, or declared capabilities — is attributable to a reviewed change. This is the TV instance of shared `REL-NATIVECONFIG-1`, and an unexplained manifest diff is a blocker, not a note (shared `REL-NATIVECONFIG-2`).
- `REACT-TV-PKG-3` **Manifest metadata required by the target platform is present, valid, and consistent with the app's actual behavior** — including the fields the vendor requires for store acceptance (application id, version, entry point, icons and store assets, and any declared memory requirement or capability). A privilege or permission declared but unused is removed; a capability the app actually uses but does not declare is a defect. The vendor's current documentation defines the required set.
- `REACT-TV-PKG-4` **The app version in the vendor manifest is bumped together with the package version for every release**, and matches it — a manifest version that lags the package version ships as the wrong build. Shared `REL-VERSION-1` and `REL-VERSION-2` apply to the TV manifest and changelog.
- `REACT-TV-PKG-5` **Signing material never lives in the repository.** Author and distributor certificates, private keys, keystores, store credentials, and vendor developer-account tokens are held outside source control and injected at build time; a committed certificate or key is a `SEC-SECRETS-1` violation and, once committed, is rotated rather than merely deleted (shared `SEC-SECRETS-4`). Certificate paths and passwords are not hardcoded into a committed build script (shared `SEC-SECRETS-3`).
- `REACT-TV-PKG-6` **Nothing secret is baked into the packaged app.** A TV package is a locally installed, unpacked bundle of application code — everything inside it is readable, so a build-time constant in it is public (shared `SEC-SECRETS-2`, `REACT-API-BASEQ-6`). A call that genuinely needs a secret goes through a server, never the TV client. Release builds apply the platform's available minification and disable debug/inspection channels (shared `SEC-HARDEN-2`, `SEC-HARDEN-3`).
- `REACT-TV-PKG-7` **Environment configuration is resolved per target, and the shipped package's target is verified before submission.** A TV package built against a staging API and submitted to a store is a release-blocking error; environment variables for each TV target are set deliberately (shared `REL-ENV-1`) and no real secret is committed among them (shared `REL-ENV-2`).
- `REACT-TV-PKG-8` **Store submission and distribution metadata changes are recorded for the release** — store listing assets, description, release notes, and declared capabilities per vendor store — as the TV reading of shared `REL-STORE-1`. The vendor's certification requirements are treated as release criteria, and an unverifiable item defaults to No-Go (shared `REL-VERDICT-1`).
